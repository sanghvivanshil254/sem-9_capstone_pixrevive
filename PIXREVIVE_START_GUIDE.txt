11. TROUBLESHOOTING (only observed or code-verified causes)
----------------------------------------------------------------------
Segfault in the full suite (observed 3/3 runs, 2026-10-18): FIXED 2026-10-20.
    Three consecutive full-suite runs through scripts/run_tests.sh
    died with "Windows fatal exception: access violation" at ~78%
    progress, entering tests/test_restoration_regressions.py
    (logs .freebuff/fullsuite_guide.log, fullsuite_run2.log,
    fullsuite_run3.log). Pytest's faulthandler traceback showed the
    fatal frame in the DDColor colorizer loader thread every time
    (_load_colorizer -> ddcolor checkpoint load / model build),
    racing the fast-loader thread that loads GFPGAN/Real-ESRGAN/
    defect_segmenter - i.e. the TWO concurrent daemon loader
    threads RestorationPipeline.__init__ starts
    doing torch native I/O/allocation simultaneously. NOT a GPU
    issue and not parallel workers: tests/conftest.py forces
    PIXREVIVE_DEVICE=cpu and the suite runs single-process.
    THE FIX: both loader threads now serialize behind one
    threading.Lock (self._load_lock in
    backend/ai/pipeline/restoration_pipeline.py). After the fix,
    two consecutive full-suite runs completed cleanly (449 passed,
    1 skipped each; no access violation) - the only failure is the
    pre-existing Case11 fixture issue described in section 5.
    Historical workaround (kept for reference): run the heavy file standalone
    (PYTHONPATH=backend python -m pytest
    tests/test_restoration_regressions.py), then invoke run_tests.sh
    with --deselect for the already-passed file's nodes, or simply
    re-run the part after the crash with run_tests.sh + a node
    range. A re-run after a crash with --lf finishes the remainder.
CUDA OOM on a 4 GB card: tests/conftest.py documents that running
    many pipeline instances on CUDA OOMs nondeterministically.
    It forces PIXREVIVE_DEVICE=cpu for the whole pytest run, and
    warns that an explicit PIXREVIVE_DEVICE=cuda WILL BE HONORED
    if you export it deliberately. If GPU tests die with "memory
    allocation failed ... free: 0", drop back to the default CPU
    run.
Stale backend after a .py edit: uvicorn is started WITHOUT
    --reload in both README instructions and run.bat. Restart the
    backend process to pick up code changes (both sources agree).
Port in use: not handled anywhere in code (uvicorn will just
    error). Check with netstat or taskkill the previous python.
Missing weights: run.bat auto-runs download_weights.py if
    backend/ai/weights/GFPGANv1.4.pth is missing, and the main
    pipeline separately reports model==false with a load_errors
    entry at /api/health. A bare-model "false" + empty
    load_errors (like ddcolor) is honest degradation, not OK to
    ignore permanently.
CORS / wrong backend URL: the frontend targets
    import.meta.env.VITE_API_BASE || http://localhost:8000
    (frontend/src/services/api.js). If you move the backend,
    either set VITE_API_BASE in frontend/.env.local (file exists
    as .env.example) or rely on the default ports matching. The
    backend's default CORS allowlist covers 5173/4173
    (backend/main.py). Not verified: cross-origin behavior for
    https targets.
Wrong python: bare `python` on PATH is explicitly forbidden by
    the README; always use the full path to
    "C:\Program Files\Python312\python.exe" or the surrogate
    pytest.exe path shown in section 6.
VRAM budget for a full cuda restore run on a 4 GB card: the lena
    fixture peaked at 3405 MB / 4096 MB measured at 1 Hz
    (.freebuff/vram_lena.csv, 2026-10-20) with GPU util 99%. That is
    inside budget but close — close other GPU apps first; an OOM here
    looks like a hung request (see CUDA OOM entry above).
Dependencies "broken" (pip check noise): basicsr/facexlib/gfpgan
    monoliths demand opencv-python although the project pins
    opencv-contrib-python; the tracker note is inside
    backend/requirements.txt itself (choose contrib, never both).
experimental/orchestrator/*: from-repo test collection errors
    (missing ai.orchestrator module) - treating this as a known
    draft area; only tests/ is the supported suite.
